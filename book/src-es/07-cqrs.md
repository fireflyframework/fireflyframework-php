# CQRS: Comandos y Consultas {.chtitle}

Al terminar este capítulo conocerás la forma de los dos buses de `firefly/cqrs` (`CommandBus::send` / `QueryBus::ask`), cómo `#[CommandHandler]`/`#[QueryHandler]` registran un manejador como bean de DI y como destino de despacho a la vez — con el tipo de mensaje manejado *inferido* del propio parámetro `handle()` del manejador —, exactamente qué aspecto tiene la tubería acotada que ejecuta cada bus, cómo la excepción propia de un manejador llega hasta quien lo llama envuelta en una `CommandProcessingException`/`QueryProcessingException`, y cómo `HandlerScanner` compila el descubrimiento de manejadores en un manifiesto que `firefly:cache` escribe justo al lado de los manifiestos de componentes y rutas que ya conociste en los Capítulos 2 y 4.

!!! note "Término nuevo: CQRS"
    **Command Query Responsibility Segregation** (segregación de responsabilidad entre comandos y consultas) trata las escrituras y las lecturas como dos tipos distintos de mensaje con dos caminos de despacho distintos — un **comando** es una intención de cambiar el modelo de escritura y devuelve como mucho un id o un recuento; una **consulta** es una lectura pura que nunca muta nada. `firefly/cqrs` le da a cada uno su propio bus, su propio atributo de manejador y su propia tubería, así que los dos nunca se mezclan por accidente en un mismo punto de llamada.

---

## Dos buses, una misma forma

Ambos buses son puertos de un solo método:

```php
interface CommandBus
{
    public function send(object $command): mixed;
}
```

```php
interface QueryBus
{
    public function ask(object $query): mixed;
}
```

`send` es el verbo del lado de escritura; `ask` es el verbo del lado de lectura — elegido deliberadamente en vez del más obvio `query()`, que colisionaría con el propio `Model::query()` de Eloquent en cada punto de llamada dentro de un repositorio. Ninguna de las dos interfaces exige que su mensaje implemente nada: `Firefly\Cqrs\Command\Command` y `Firefly\Cqrs\Query\Query` existen puramente como marcadores documentales *opcionales* —

```php
interface Command {}
```

— así que un comando es libre de ser exactamente lo que ya es `Lumen\Application\Command\OpenWallet`: un DTO `final readonly` sin clase base ni interfaz alguna:

```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Command;

use Lumen\Domain\Currency;

/**
 * Command: open a new wallet for an owner in a given currency. A plain readonly DTO — the CQRS bus needs no marker
 * interface (per docs/modules/cqrs.md); the handler is resolved by the command's class-string. The wallet id is
 * generated by OpenWalletHandler and returned to the caller.
 */
final readonly class OpenWallet
{
    public function __construct(
        public string $ownerId,
        public Currency $currency,
    ) {}
}
```

Despachar uno es una única llamada, ya venga de un controlador, de una prueba o de otro servicio:

```php
/** @var CommandBus $commands */
$walletId = $commands->send(new OpenWallet('owner-A', Currency::EUR));
```

`$commands->send()` devuelve *lo que sea que devuelva el manejador* — aquí, el id de monedero recién acuñado — porque `send()`/`ask()` están tipados `mixed`. El bus en sí no tiene ni idea de qué significa un `OpenWallet`; eso es enteramente trabajo del manejador, que es exactamente lo que construye la siguiente sección.

## Manejadores: un atributo, dos trabajos

`#[CommandHandler]` y `#[QueryHandler]` **especializan** ambos `#[Component]` del Capítulo 2 — lo *extienden*, en vez de simplemente parecerse a él:

```php
#[Attribute(Attribute::TARGET_CLASS)]
final class CommandHandler extends Component
{
    public function __construct(public readonly ?string $command = null)
    {
        parent::__construct();
    }
}
```

```php
#[Attribute(Attribute::TARGET_CLASS)]
final class QueryHandler extends Component
{
    public function __construct(public readonly ?string $query = null)
    {
        parent::__construct();
    }
}
```

Gracias a ese `extends Component`, un solo atributo hace **dos** trabajos independientes a la vez: `ComponentScanner` (Capítulo 2) descubre la clase mediante la coincidencia `ReflectionAttribute::IS_INSTANCEOF`, exactamente como lo haría con un `#[Service]`, así que el manejador se convierte en un bean singleton inyectado por constructor **sin necesitar un `#[Service]` aparte** — y el propio `HandlerScanner` de `firefly/cqrs` lee ese mismo atributo para construir la tabla de despacho de comandos/consultas. Aquí está el manejador completo y real detrás de `OpenWallet` — `samples/lumen/src/Application/Command/OpenWalletHandler.php`:

```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Command;

use Firefly\Cqrs\Attributes\CommandHandler;
use Firefly\Data\Transaction\Attributes\Transactional;
use Lumen\Domain\Wallet;
use Lumen\Infrastructure\WalletRepository;

/**
 * Handles OpenWallet: mints a new wallet id, opens the aggregate, and persists it. The handled command type is
 * inferred from the sole handle() parameter (HandlerScanner param inference) — no explicit #[CommandHandler(...)].
 *
 * #[Transactional] is LOAD-BEARING, not cosmetic: DefaultCommandBus opens no transaction of its own, and
 * EloquentRepository::save() only tracks the aggregate when transactionLevel() > 0. The generated transactional proxy
 * installs the TransactionTemplate that is the sole caller of DomainEventDispatcher::dispatchAfterCommit(), so without
 * this attribute the WalletOpened domain event would never publish and S5's ledger projector would never fire.
 *
 * Intentionally NOT final: the generated transactional proxy subclasses this handler (mirroring the framework's own
 * SignatureBag/TxWidget fixtures and the PlaceOrderService pattern in docs/modules/domain.md).
 */
#[CommandHandler]
class OpenWalletHandler
{
    public function __construct(private readonly WalletRepository $wallets) {}

    #[Transactional]
    public function handle(OpenWallet $command): string
    {
        $id = 'wlt-'.bin2hex(random_bytes(8));
        $wallet = Wallet::open($id, $command->ownerId, $command->currency);
        $this->wallets->save($wallet);

        return $id;
    }
}
```

Fíjate en que aquí `#[CommandHandler]` no lleva **ningún argumento** — `OpenWallet::class` no se escribe en ningún sitio de este archivo. `HandlerScanner` — el único punto de reflexión de todo el paquete — resuelve el tipo de mensaje manejado leyendo el propio parámetro de `handle()`:

```php
final class HandlerScanner
{
    private function messageType(ReflectionClass $reflection, ?string $explicit, string $handlerClass): string
    {
        if ($explicit !== null) {
            return $explicit;
        }

        if (! $reflection->hasMethod('handle')) {
            throw new CqrsConfigurationException("Handler [{$handlerClass}] declares no public handle() method. Add handle(<Message>) or an explicit #[CommandHandler(Message::class)].");
        }

        $parameters = $reflection->getMethod('handle')->getParameters();
        if (count($parameters) !== 1) {
            throw new CqrsConfigurationException("Handler [{$handlerClass}]::handle() must take exactly one message parameter, got ".count($parameters).'.');
        }

        $type = $parameters[0]->getType();
        if (! $type instanceof ReflectionNamedType || $type->isBuiltin()) {
            throw new CqrsConfigurationException("Cannot infer the message type for [{$handlerClass}]::handle() from its parameter. Annotate #[CommandHandler(Message::class)] / #[QueryHandler(Message::class)] explicitly.");
        }

        return $type->getName();
    }
}
```

Es la misma regla que el Capítulo 6 ya te mostró para el escáner gemelo de `#[EventListener]`. Un `#[CommandHandler(OpenWallet::class)]` explícito siempre gana si está presente — útil cuando `handle()` recibe un tipo base compartido o un parámetro `object` que el escáner no puede estrechar — pero para el caso común de un manejador, un mensaje concreto, un parámetro tipado, nunca escribes el nombre de la clase dos veces. Equivócate en la forma — sin método `handle()`, más de un parámetro, un tipo de parámetro escalar/unión que el escáner no puede resolver a una clase — y `HandlerScanner` lanza `CqrsConfigurationException` en **tiempo de caché**, no en alguna petición posterior.

El lado de consultas es la imagen especular, y lee una consulta sin efecto secundario alguno — `GetBalanceHandler`, código real y distribuido:

```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Query;

/**
 * Query: read a wallet's current balance in minor units. GetBalanceHandler returns null for an unknown wallet.
 */
final readonly class GetBalance
{
    public function __construct(public string $walletId) {}
}
```

```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Query;

use Firefly\Cqrs\Attributes\QueryHandler;
use Lumen\Infrastructure\WalletRepository;

/**
 * Handles GetBalance: reads the aggregate through the port and returns its balance in minor units, or null when no
 * such wallet exists. A pure read — no #[Transactional]; the query type is inferred from the handle() parameter.
 */
#[QueryHandler]
final class GetBalanceHandler
{
    public function __construct(private readonly WalletRepository $wallets) {}

    public function handle(GetBalance $query): ?int
    {
        $wallet = $this->wallets->findById($query->walletId);

        return $wallet?->balanceMoney()->minorUnits;
    }
}
```

`GetBalanceHandler` es `final` y no lleva ningún `#[Transactional]` — una consulta nunca muta estado, así que no hay ninguna unidad de trabajo que delimitar y nada que un proxy pueda interceptar. `GetLedgerHandler` (detrás del `WalletController::ledger()` del Capítulo 4) tiene la misma forma, leyendo directamente filas de `LedgerEntry`:

```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Query;

use Firefly\Cqrs\Attributes\QueryHandler;
use Lumen\Domain\LedgerEntry;

/**
 * Handles GetLedger: returns the wallet's ledger rows in insertion order. S5's projector writes `ledger_entries`, so
 * this reads the projected rows directly (an empty list for a wallet with no entries yet). A pure read —
 * no #[Transactional]; the query type is inferred from the handle() parameter.
 */
#[QueryHandler]
final class GetLedgerHandler
{
    /** @return list<LedgerEntry> */
    public function handle(GetLedger $query): array
    {
        return array_values(
            LedgerEntry::query()
                ->where('wallet_id', $query->walletId)
                ->orderBy('id')
                ->get()
                ->all()
        );
    }
}
```

!!! laravel "Paridad con Laravel"
    Laravel puro no tiene ninguna separación entre lectura y escritura en la capa de despacho — o bien haces `dispatch()` de un job en cola o llamas directamente a un método de servicio, y nada impide que un objeto "consulta" mute algo silenciosamente. `#[CommandHandler]`/`#[QueryHandler]` convierten esa separación en un concepto de primera clase, descubierto por atributo: un manejador de consulta que intentara llamar a `$this->wallets->save(...)` seguiría compilando, pero sería una señal de alarma obvia en cualquier revisión de código, porque nada en la tubería de `QueryBus::ask()` (sin transacción, sin drenaje de eventos de dominio) lo respalda.

## La tubería acotada

Ninguno de los dos buses es una simple llamada a función sobre el manejador. `DefaultCommandBus::send()` — la implementación distribuida — ejecuta una secuencia pequeña y fija de colaboradores alrededor del despacho:

```php
final class DefaultCommandBus implements CommandBus
{
    public function __construct(
        private readonly HandlerRegistry $registry,
        private readonly MessageValidator $validator,
        private readonly CommandAuthorizer $authorizer,
        private readonly CorrelationContext $correlation,
        private readonly CqrsMetrics $metrics,
    ) {}

    public function send(object $command): mixed
    {
        $prior = $this->correlation->begin();
        $startedAt = microtime(true);

        try {
            $this->validator->validate($command);
            $this->authorizer->authorize($command);

            $handler = $this->registry->findCommandHandler($command::class);
            $result = $handler($command);

            $this->metrics->recordCommandSuccess($command, microtime(true) - $startedAt);

            return $result;
        } catch (Throwable $e) {
            $this->metrics->recordCommandFailure($command, microtime(true) - $startedAt);

            throw $e instanceof CommandProcessingException ? $e : new CommandProcessingException($command::class, $e);
        } finally {
            $this->correlation->end($prior);
        }
    }
}
```

Léelo como **correlacionar → validar → autorizar → resolver e invocar el manejador → métricas**, envuelto en un `try`/`catch`/`finally` que garantiza que el id de correlación se restaura pase lo que pase. `DefaultQueryBus::ask()` tiene la misma forma con un paso extra — un cortocircuito de caché — insertado entre autorizar e invocar:

```php
final class DefaultQueryBus implements QueryBus
{
    public function ask(object $query): mixed
    {
        $prior = $this->correlation->begin();
        $startedAt = microtime(true);

        try {
            $this->validator->validate($query);
            $this->authorizer->authorize($query);

            $key = $query instanceof Cacheable ? $query->cacheKey() : null;

            if ($key !== null) {
                $cached = $this->cache->get($key);
                if ($cached !== null) {
                    $this->metrics->recordQuerySuccess($query, microtime(true) - $startedAt);

                    return $cached;
                }
            }

            $handler = $this->registry->findQueryHandler($query::class);
            $result = $handler($query);

            if ($key !== null) {
                $this->cache->put($key, $result, $this->cacheTtl);
            }

            $this->metrics->recordQuerySuccess($query, microtime(true) - $startedAt);

            return $result;
        } catch (Throwable $e) {
            $this->metrics->recordQueryFailure($query, microtime(true) - $startedAt);

            throw $e instanceof QueryProcessingException ? $e : new QueryProcessingException($query::class, $e);
        } finally {
            $this->correlation->end($prior);
        }
    }
}
```

Todos los colaboradores excepto el propio `HandlerRegistry` son, por defecto, un **no-op**, así que la tubería es una cadena de etapas que puedes ir activando de una en una, en vez de un framework de todo-o-nada:

| Etapa | Por defecto | Qué la enciende |
|---|---|---|
| Validación | Se omite salvo que el mensaje implemente `Validatable` | El `Validator` distribuido de `firefly/validation` |
| Autorización | `AllowAllAuthorizer` — permite todo | `SecurityCommandAuthorizer`/`SecurityQueryAuthorizer` de `firefly/security` (Capítulo 10) |
| Correlación | Siempre activa — un id uuid4 por despacho, restaurado después | Nada que activar; se estampa en `x-correlation-id` cuando un evento de dominio llega al bus de eda (Capítulo 8) |
| Métricas | `NoOpCqrsMetrics` | `firefly/observability` (un capítulo posterior) |
| Caché de consultas | `NoOpQueryCache` — siempre falla | Un futuro adaptador de `firefly/cache` |

Ninguno de los dos buses abre una transacción, y ninguno de los dos drena eventos de dominio. `#[Transactional]` sobre `OpenWalletHandler::handle()` de arriba hace ese trabajo enteramente por su cuenta, a través del proxy generado que el Capítulo 9 explica en detalle — el bus es completamente ajeno a él, y se comportaría idénticamente si `handle()` fuera un método plano, sin proxy, que llamara a `DB::beginTransaction()` a mano.

## Cuando un manejador lanza: envoltura que preserva la categoría

El `handle()` de `WithdrawHandler` puede fallar de dos formas muy distintas — puede que el monedero no exista, o que la propia invariante de no-sobregiro del dominio rechace el importe. En cualquier caso, el bloque `catch` de `send()` envuelve lo que se haya lanzado:

```php
final class CommandProcessingException extends CqrsException
{
    public function __construct(string $commandClass, Throwable $cause)
    {
        parent::__construct(
            "Processing command [{$commandClass}] failed: {$cause->getMessage()}",
            'COMMAND_PROCESSING_ERROR',
            $cause instanceof FireflyException ? $cause->httpStatus() : 500,
            $cause instanceof FireflyException ? $cause->category() : ErrorCategory::Internal,
            $cause instanceof FireflyException ? $cause->severity() : ErrorSeverity::Error,
            $cause,
        );
    }
}
```

Tres cosas merecen destacarse. Primero, la causa siempre está disponible en `getPrevious()` — el quinto argumento del constructor hacia el padre — así que nada del fallo original se pierde, solo se envuelve. Segundo, esto **preserva la categoría**: cuando la causa es una `FireflyException` (todas las excepciones del kernel lo son), su propio `httpStatus()`/`category()`/`severity()` se copian sobre el envoltorio en vez de recaer en un genérico `500`/`Internal`. Una `ResourceNotFoundException` (404, negocio) lanzada por un id de monedero desconocido sigue renderizándose como una respuesta de detalles de problema 404 incluso después de ser envuelta — el bus añade contexto, nunca enmascara el fallo. Tercero, `send()` comprueba `$e instanceof CommandProcessingException` antes de envolver, así que un despacho de comando anidado (un manejador que a su vez llama a `$commands->send(...)`) nunca queda envuelto dos veces en dos capas de la misma excepción. `QueryProcessingException` es el gemelo del lado de lectura, idéntico en forma.

`HandlerRegistry` lanza sus propias excepciones, más estrechas, para un error de **cableado** en vez de un fallo de negocio — un mensaje sin mapear enviado a través del bus:

```php
final class HandlerRegistry
{
    public function findCommandHandler(string $commandClass): callable
    {
        return $this->commandHandlers[$commandClass] ?? throw new CommandHandlerNotFoundException($commandClass);
    }
}
```

`CommandHandlerNotFoundException`/`QueryHandlerNotFoundException` son ambas `ErrorCategory::Framework`, `500` — una señal genuinamente distinta de un `409` de `ConflictException`: la primera significa "nunca se registró ningún manejador para este mensaje", la segunda significa "algo *sí* se registró, y correctamente rechazó la petición". El registro también rechaza de plano un **segundo** registro para la misma clase de mensaje:

```php
final class HandlerRegistry
{
    public function registerCommandHandler(string $commandClass, callable $invoker): void
    {
        if (isset($this->commandHandlers[$commandClass])) {
            throw new CqrsConfigurationException("Duplicate command handler registered for message [{$commandClass}]. One command maps to exactly one handler.");
        }

        $this->commandHandlers[$commandClass] = $invoker;
    }
}
```

Un comando, un manejador — aplicado en tiempo de cableado, no dejado a merced de cuál registro se haya ejecutado último.

!!! tip "Desenvolver la causa en una prueba"
    Una prueba que quiere afirmar *por qué* se rechazó un comando llega directamente más allá del envoltorio con `getPrevious()`. `samples/lumen/tests/Application/TransferSecurityTest.php` hace exactamente esto para un `#[PreAuthorize]` denegado (el Capítulo 10 explica la protección en sí):

```php
$denied = null;
try {
    $commands->send(new Withdraw($walletId, 1000));
} catch (CommandProcessingException $e) {
    $denied = $e;
}

expect($denied)->toBeInstanceOf(CommandProcessingException::class);
expect($denied?->getPrevious())->toBeInstanceOf(AuthorizationException::class);
```

El tipo exterior te dice *qué operación del bus* falló; el tipo interior — alcanzado vía `getPrevious()` — te dice *por qué*.

## Compilado, no reflexionado: `HandlerScanner` → `HandlerManifest` → `firefly:cache`

`HandlerScanner` es el **único** punto de reflexión en `packages/cqrs/src` (la misma invariante forzada por grep que el Capítulo 6 describió para `firefly/domain`). Recorre una vez las raíces PSR-4 de la aplicación, resuelve cada `#[CommandHandler]`/`#[QueryHandler]` (ejecutando exactamente la inferencia de `messageType()` que acabas de leer) en un `HandlerDescriptor`, y entrega la lista completa a `HandlerManifestCompiler`, que la `var_export()`a en un archivo PHP de array plano — la misma técnica sin reflexión que el Capítulo 2 introdujo para el manifiesto de componentes y el Capítulo 3 para `#[ConfigProperties]`.

Nunca ejecutas `HandlerScanner` tú mismo. Es uno de los **doce** pares escáner/compilador que `php artisan firefly:cache` orquesta en un solo paso, junto al de componentes/contexto, rutas, propiedades de configuración y (del Capítulo 9) el transaccional:

```bash
$ php artisan firefly:cache
firefly:cache — wrote 12 manifest(s) + 1 proxy(ies) to /path/to/my-app/bootstrap/cache/firefly
```

El archivo compilado aterriza en `bootstrap/cache/firefly/handlers.php`; `FireflyCacheServiceProvider` lo vincula directamente sobre la entrada del contenedor `HandlerManifest` — sobrescribiendo incondicionalmente el `HandlerManifest` **vacío** por defecto que `CqrsWiringProvider` vincula cuando todavía no existe ninguna caché (el mismo patrón de retirada al estilo `#[ConditionalOnMissingBean]` que el Capítulo 2 te mostró para los beans, aplicado aquí a todo un manifiesto compilado). `CqrsHandlerWiringPass` recorre entonces ese manifiesto en el arranque y llena el `HandlerRegistry` que conociste arriba con un invocador por descriptor — cada invocador resuelve su bean manejador **de nuevo desde el contenedor en cada despacho**, nunca en caché en tiempo de cableado, así que un manejador `#[Transactional]` como `OpenWalletHandler` siempre se observa a través de su proxy generado (Capítulo 9), nunca a través de la clase desnuda, sin proxy.

Equivócate en esto en una aplicación — añade un manejador, olvida volver a ejecutar `firefly:cache` — y el mensaje que debería haber manejado no resuelve nada: `HandlerRegistry::findCommandHandler()` nunca ve el nuevo descriptor, y despachar ese comando lanza `CommandHandlerNotFoundException` hasta que se regenere la caché. Falla ruidosamente en tiempo de caché (un manejador mal formado) o falla ruidosamente en tiempo de despacho (una caché obsoleta) — nunca un no-op silencioso.

## Lo que aprendiste {.recap}

| Concepto | Qué hace |
|---|---|
| `CommandBus::send(object): mixed` / `QueryBus::ask(object): mixed` | Los dos puertos de despacho; un comando puede mutar y devuelve como mucho un id, una consulta nunca muta |
| `#[CommandHandler]` / `#[QueryHandler]` | Especializan `#[Component]` — un solo atributo registra el manejador como bean de DI **y** como destino de despacho |
| Inferencia del tipo de mensaje | `HandlerScanner` lee el único parámetro de `handle()` a menos que se dé una cadena de clase explícita |
| La tubería acotada | correlacionar → validar → autorizar → (obtener de caché, solo consultas) → resolver e invocar → (guardar en caché, solo consultas) → métricas |
| `CommandProcessingException` / `QueryProcessingException` | Envoltorios que preservan la categoría; el fallo original siempre es alcanzable vía `getPrevious()` |
| `HandlerRegistry` | Una clase de comando/consulta se mapea a exactamente un manejador — un registro duplicado falla ruidosamente en tiempo de cableado |
| `HandlerScanner` → `HandlerManifest` | El único punto de reflexión; compilado por `firefly:cache` (uno de doce pares escáner/compilador) en un manifiesto sin reflexión |

## Ponlo en práctica {.exercises}

1. **Provoca `CommandHandlerNotFoundException`.** En una copia de trabajo del proyecto (no en el paquete distribuido `samples/lumen`), define una nueva clase de comando sin ningún `#[CommandHandler]` en toda la aplicación, despáchala a través de `CommandBus::send()`, y confirma que obtienes una `CommandHandlerNotFoundException` sin envolver en nada (la lanza directamente el registro, antes de que el propio bloque `catch` del bus pudiera envolver el fallo de un manejador).
2. **Fuerza un `handle()` ambiguo.** Dale a una clase `#[QueryHandler]` un método `handle()` con dos parámetros (o un parámetro tipado `object`) y ejecuta `php artisan firefly:cache`. Confirma que falla ruidosamente con `CqrsConfigurationException` nombrando la clase y el método exactos, en vez de omitir el manejador silenciosamente.
3. **Lee el manifiesto compilado.** Tras ejecutar `firefly:cache` en un proyecto con `OpenWalletHandler` y `GetBalanceHandler` presentes, abre `bootstrap/cache/firefly/handlers.php` y encuentra ambas entradas. Empareja el campo `kind` de cada array (`'command'` o `'query'`) con el enum `HandlerKind` que describió este capítulo.
