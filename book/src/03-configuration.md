# Configuration, Profiles & Secrets {.chtitle}

By the end of this chapter you will know how LaraFly's `Config` wraps Laravel's own configuration repository with fail-fast typed accessors, how `#[ConfigProperties]` binds a whole config subtree onto a typed, injectable DTO, how `#[Value]` resolves an individual scalar once `firefly/config` is installed, how active profiles are resolved and how a bean can be gated to one of them, and — closing the loop with Chapter 2 — exactly how a `#[ConfigProperties]` DTO travels from source attribute to a compiled, zero-reflection manifest.

!!! note "New term: configuration subtree"
    A **subtree** is everything nested under one dotted key in Laravel's config array — `mail.host`, `mail.port`, and `mail.tls` are all part of the `mail` subtree. `#[ConfigProperties]` binds one whole subtree onto one DTO in a single step, instead of reading each key by hand.

---

## Configuration is still Laravel's configuration

LaraFly does not replace Laravel's configuration system — it rides on top of it. Every `config/*.php` file, every `env('...')` call, every `.env` variable you already know from a plain Laravel application works exactly the same way in a LaraFly one. `firefly/config`'s job is narrower and more specific: it gives you a **typed, fail-fast accessor** over that same repository, a way to **bind a whole subtree onto a DTO**, and a **config-backed resolver** for the `#[Value]` attribute Chapter 2 introduced.

You already met the smallest possible example of this in the Quick Start. `app/GreetingProperties.php`, generated by `composer create-project firefly/skeleton`, is a real, shipped `#[ConfigProperties]` DTO:

```php
<?php

declare(strict_types=1);

namespace App;

use Firefly\Config\Attributes\ConfigProperties;

/**
 * Binds the `greeting.*` configuration subtree onto this readonly DTO and registers it as a container
 * singleton, so it can be constructor-injected wherever GreetingProperties is requested.
 */
#[ConfigProperties('greeting')]
final readonly class GreetingProperties
{
    public function __construct(public string $salutation = 'Hello') {}
}
```

This chapter explains, in depth, everything that one small file quietly does for you.

## Typed access with `Config`

Before reaching for a DTO, it helps to see the layer directly underneath it. `Firefly\Config\Config` wraps `Illuminate\Contracts\Config\Repository` — the very same config repository `config()` reads from in a plain Laravel app — with four typed getters: `string()`, `int()`, `bool()`, and `array()`. Each one is **fail-fast**: a required key (no default supplied) that is missing, or a value that cannot be coerced to the requested type, throws `ConfigurationException` immediately, instead of handing you `null` or a silently wrong type three call frames later.

```php
$config->string('mail.host');          // required — throws ConfigurationException if absent
$config->int('mail.port', 25);         // falls back to 25 when the key is absent
$config->bool('mail.tls', false);
$config->array('mail.recipients', []);
```

`Config` is registered as a container singleton, so it constructor-injects anywhere:

```php
use Firefly\Config\Config;
use Firefly\Container\Attributes\Service;

#[Service]
final class MailerBootstrap
{
    public function __construct(private readonly Config $config) {}

    public function host(): string
    {
        return $this->config->string('mail.host', 'localhost');
    }
}
```

!!! note "Note"
    `Config::has()` and `Config::get()` behave exactly like Laravel's own `Repository::has()`/`Repository::get()` — `Config` adds typed, fail-fast wrappers around them, it does not replace or reinterpret Laravel's own dot-notation resolution.

`string()`/`int()`/`bool()`/`array()` are enough for occasional reads. They do not scale past a handful of scattered calls: each one is an isolated lookup with no shared type information, a typo in a key string surfaces only when that exact line runs, and a service that needs five related settings ends up with five separate `$config->...()` calls sprinkled through its constructor body. `#[ConfigProperties]` solves exactly this.

## `#[ConfigProperties]`: binding a subtree onto a typed DTO

`#[ConfigProperties(string $prefix)]` is a class-level attribute (`Firefly\Config\Attributes\ConfigProperties`). It names the dotted config prefix the class binds from; the framework reads that subtree, matches each key to a constructor parameter by name, coerces scalars to the declared type, and registers the resulting instance as a container singleton — so any bean that asks for the DTO type receives the bound configuration, fully typed, with no `config('...')` call anywhere in its own body.

Applying the same pattern to a business setting is just as short as `GreetingProperties` was. Suppose Lumen wants a configurable daily transfer ceiling:

```php
<?php

declare(strict_types=1);

namespace Lumen\Domain;

use Firefly\Config\Attributes\ConfigProperties;

/**
 * Binds the `wallet.*` configuration subtree — a per-day transfer ceiling in minor units and the
 * default currency assigned to a wallet opened without one — onto this readonly DTO.
 */
#[ConfigProperties('wallet')]
final readonly class WalletProperties
{
    public function __construct(
        public int $dailyTransferLimitMinor = 1_000_000,
        public string $defaultCurrency = 'EUR',
    ) {}
}
```

and the matching config file, `config/wallet.php`:

```php
<?php

declare(strict_types=1);

return [
    'daily_transfer_limit_minor' => env('WALLET_DAILY_TRANSFER_LIMIT_MINOR', 1_000_000),
    'default_currency' => env('WALLET_DEFAULT_CURRENCY', 'EUR'),
];
```

`TransferHandler` (Chapter 4 and 6 build the rest of it) can now depend on `WalletProperties` directly:

```php
use Firefly\Container\Attributes\Service;
use Lumen\Domain\WalletProperties;

#[Service]
final class TransferLimitGuard
{
    public function __construct(private readonly WalletProperties $properties) {}

    public function isWithinDailyLimit(int $amountMinor): bool
    {
        return $amountMinor <= $this->properties->dailyTransferLimitMinor;
    }
}
```

Nothing here calls `config('wallet.daily_transfer_limit_minor')`. `WalletProperties` is a typed, self-documenting object — the constructor's own default values (`1_000_000`, `'EUR'`) double as living documentation of what the setting means when nothing overrides it, and a typo in a constructor parameter name is a PHP error at binding time, not a silently-`null` field discovered in production.

!!! laravel "Laravel parity"
    `#[ConfigProperties]` is LaraFly's counterpart to Spring Boot's `@ConfigurationProperties`. In a plain Laravel application the closest equivalent is writing your own DTO and populating it by hand from `config('wallet')` in a service provider's `register()` method; `#[ConfigProperties]` is that same idea with the boilerplate removed — the prefix is the only thing you declare, and the binder does the rest.

### How binding actually works: `ReflectionConfigBinder`

The default binder, `Firefly\Config\Binder\ReflectionConfigBinder`, resolves one constructor parameter at a time from the bound subtree array:

```php
final class ReflectionConfigBinder implements ConfigBinder
{
    private function resolveParameter(string $class, ReflectionParameter $parameter, array $config): mixed
    {
        $name = $parameter->getName();
        $value = array_key_exists($name, $config) ? $config[$name] : null;

        if ($value === null) {
            if ($parameter->isDefaultValueAvailable()) {
                return $parameter->getDefaultValue();
            }
            if ($parameter->allowsNull()) {
                return null;
            }

            throw new ConfigurationException("Missing required configuration property [{$name}] for {$class}.");
        }

        $type = $parameter->getType();
        if (! $type instanceof ReflectionNamedType) {
            return $value;
        }

        return $this->coerce($type, $value);
    }
}
```

Three rules fall out of that method body directly. A missing key with a constructor default silently uses the default — exactly why `WalletProperties`'s constructor spells out `1_000_000` and `'EUR'` rather than leaving them required. A missing key with **no** default and a non-nullable type throws `ConfigurationException` immediately, at binding time — not the first time a handler happens to touch the field. And when a constructor parameter is itself typed as another class (not a scalar) and the subtree holds an array under that key, the binder **recurses**: it calls itself on the nested class and the nested array, so a `#[ConfigProperties]` DTO can compose smaller DTOs without any extra wiring.

Scalar coercion is equally mechanical — `int`/`float`/`bool` fields are coerced from whatever the config value actually is (useful when a value arrived from an environment variable as a string), and `string` accepts anything scalar:

```php
final class ReflectionConfigBinder implements ConfigBinder
{
    private function coerce(ReflectionNamedType $type, mixed $value): mixed
    {
        if ($type->isBuiltin()) {
            return match ($type->getName()) {
                'int' => is_numeric($value) ? (int) $value : $value,
                'float' => is_numeric($value) ? (float) $value : $value,
                'bool' => is_bool($value) ? $value : filter_var($value, FILTER_VALIDATE_BOOLEAN),
                'string' => is_scalar($value) ? (string) $value : $value,
                default => $value,
            };
        }

        $nested = $type->getName();
        if (is_array($value) && class_exists($nested)) {
            return $this->bind($nested, $value);
        }

        return $value;
    }
}
```

!!! tip "The binder is a seam, not the only implementation"
    `ReflectionConfigBinder` implements a one-method interface, `Firefly\Config\Binder\ConfigBinder`. An application (or a later Firefly package) can bind a richer binder over the container — one that understands enums, or value objects with their own validation — without touching a single `#[ConfigProperties]` class. The DTOs you write never know, or need to know, which binder actually populated them.

### From attribute to compiled manifest — the same story as Chapter 2

`#[ConfigProperties]` follows the exact "reflect once, freeze into a manifest, boot from the frozen copy" shape Chapter 2 walked through for the container. `ConfigPropertiesScanner::scan()` walks your PSR-4 roots, reflects every non-abstract class, and records a `ConfigPropertiesDescriptor` — just the class name and the prefix — for each one carrying `#[ConfigProperties]`:

```php
foreach ($this->classesIn($prefix, $dir) as $class) {
    $reflection = new ReflectionClass($class);
    if ($reflection->isAbstract() || $reflection->isInterface()) {
        continue;
    }
    $attrs = $reflection->getAttributes(ConfigProperties::class);
    if ($attrs === []) {
        continue;
    }
    $descriptors[] = new ConfigPropertiesDescriptor($class, $attrs[0]->newInstance()->prefix);
}
```

`ConfigManifestCompiler` writes that list to `bootstrap/cache/firefly/config-properties.php` with the same `var_export()`-based, zero-reflection technique the component manifest used. `php artisan firefly:cache` runs this scan as one step among the twelve scanner/compiler pairs it orchestrates — you never invoke `ConfigPropertiesScanner` yourself.

At boot, `Firefly\Cli\Boot\FireflyCacheServiceProvider` loads that compiled manifest and hands it straight to `Firefly\Config\Registrar\ConfigRegistrar::register()`, which binds every descriptor's DTO as a container singleton in one pass:

```php
foreach ($manifest->properties as $descriptor) {
    $class = $descriptor->class;
    $prefix = $descriptor->prefix;

    $this->container->singleton($class, static function () use ($binder, $class, $prefix, $config): object {
        $subtree = $config->array($prefix, []);

        return $binder->bind($class, $subtree);
    });
}
```

This is the entire reason `GreetingProperties` and `WalletProperties` need no service-provider glue anywhere in your application: the compiled manifest already knows every `#[ConfigProperties]` class and its prefix, and `ConfigRegistrar` binds all of them, unconditionally, the moment the cache exists.

!!! warning "The cache matters here too"
    Exactly as Chapter 2 explained for beans, `#[ConfigProperties]` binding is driven from the **compiled** manifest — run `php artisan firefly:cache` after adding or renaming a `#[ConfigProperties]` class, the same way you would after adding a new `#[Service]`.

## `#[Value]` from real configuration

Chapter 2 introduced `#[Value]` on a bare constructor parameter — `#[Value('${MAIL_HOST:localhost}')]` — and mentioned that `firefly/container`'s own resolver only understands environment variables and small expressions. Installing `firefly/config` upgrades that resolution without touching a single `#[Value]` site in your code:

```php
use Firefly\Container\Attributes\Value;

final class Mailer
{
    public function __construct(
        #[Value('${mail.host:localhost}')] public readonly string $host,
    ) {}
}
```

`Firefly\Config\Value\ConfigValueResolver` implements the same `ValueResolver` port `firefly/container` defines, but resolves `${key:default}` against **application configuration first**, then the environment, then the literal default:

```php
if (preg_match('/^\$\{([^:}]+)(?::([^}]*))?\}$/', $expression, $m) === 1) {
    $key = $m[1];
    if ($this->config->has($key)) {
        return $this->config->get($key);
    }
    $env = getenv($key);
    if ($env !== false) {
        return $env;
    }

    return array_key_exists(2, $m) ? $m[2] : null;
}
```

`#{expr}` still evaluates a small sandboxed expression, now with a `config('key')` function registered against it, so an expression can read configuration too — `#{config('mail.port') * 2}` is valid once `firefly/config` is installed.

`ConfigRegistrar::register()` binds `ConfigValueResolver` over the container's default:

```php
$this->container->instance(ValueResolver::class, new ConfigValueResolver($this->config));
```

`firefly/container`'s own registrar only binds its `DefaultValueResolver` **if none is already bound** — so the config-backed resolver, once `firefly/config` registers it, always wins, and `${mail.host:localhost}` now reads `config('mail.host')` first, the environment second, and only falls back to the literal `localhost` if neither is set.

!!! laravel "Laravel parity"
    `#[Value('${mail.host:...}')]` reading application config first is the closest LaraFly equivalent to Spring's `@Value("${...}")` reading `application.yaml`. In a plain Laravel application the corresponding idiom is simply `config('mail.host')` called at the point of use — `#[Value]` gets you the same resolved value, but declared once on the constructor parameter, alongside the rest of the class's dependencies.

## Profiles

A **profile** is a named environment — `local`, `testing`, `staging`, `prod` — and LaraFly gives you a small, focused vocabulary for reading which ones are currently active, independent of any one config key.

`Firefly\Config\Profile\ProfileResolver::resolve()` returns a `Profiles` value object, using a fixed precedence: the `FIREFLY_PROFILES_ACTIVE` environment variable (comma-separated, for more than one active profile) if set; otherwise the single Laravel `APP_ENV` value; otherwise the implicit `default` profile.

```php
use Firefly\Config\Profile\ProfileResolver;

$profiles = (new ProfileResolver())->resolve();

$profiles->isActive('prod');   // bool
$profiles->all();              // list<string>
$profiles->isEmpty();          // bool
```

```php
final readonly class Profiles
{
    public function __construct(public array $active) {}

    public function isActive(string $profile): bool
    {
        return in_array($profile, $this->active, true);
    }
}
```

!!! laravel "Laravel parity"
    `FIREFLY_PROFILES_ACTIVE` falling back to `APP_ENV` means every existing Laravel application already has an active profile without adding a single environment variable: `APP_ENV=production` in your `.env` file is already, today, LaraFly's `prod` profile. `FIREFLY_PROFILES_ACTIVE` exists for the case Laravel's single `APP_ENV` cannot express on its own — activating more than one profile at a time.

### Gating a component to a profile

Knowing which profiles are active becomes genuinely useful once a component's very presence in the container can depend on it. `#[ConditionalOnProfile]` — from `firefly/context`, the boot-engine package Chapter 2 mentioned in passing — gates a `#[Component]` (or a `#[Configuration]`/`#[Bean]`) on one or more profiles:

```php
use Firefly\Container\Attributes\Component;
use Firefly\Context\Condition\Attributes\ConditionalOnProfile;

#[Component]
#[ConditionalOnProfile('local', 'testing')]
final class InMemoryMailer {}
```

`InMemoryMailer` only enters the container when `local` **or** `testing` is among the active profiles — the condition is a simple "any listed profile is active" match, evaluated by the same `ConditionEvaluator` that evaluates `#[ConditionalOnProperty]`, `#[ConditionalOnClass]`, and `#[ConditionalOnMissingClass]`. On `prod`, the class is never even instantiated: it is filtered out of the `BeanDefinitionRegistry` before the container is built, not merely left unresolved.

!!! laravel "Laravel parity"
    `#[ConditionalOnProfile]` is the closest LaraFly gets to Spring's `@Profile`. In plain Laravel the nearest equivalent is an `if (app()->environment('local', 'testing'))` guard inside a service provider's `register()` method — `#[ConditionalOnProfile]` moves that same decision onto the class itself, so a component's environment-scoping is visible right next to its definition rather than in a separate provider file.

## Keeping secrets out of files

Everything this chapter has shown reads through `env()` at some point — `env('WALLET_DAILY_TRANSFER_LIMIT_MINOR', ...)` in `config/wallet.php`, `${mail.host:localhost}` falling through to the environment, `FIREFLY_PROFILES_ACTIVE` itself. This is deliberate, and it is the same discipline any Laravel application should already follow: configuration that is safe to commit — ports, feature flags, default currencies — belongs in a `config/*.php` file; anything that grants access — database passwords, API keys, JWT signing secrets — belongs in `.env`, which is never committed, and is supplied differently (real files locally, injected secrets in CI/CD and production) per environment.

!!! warning "Never commit secrets"
    `#[ConfigProperties]` and `#[Value]` both ultimately read whatever your `config/*.php` files return — if a config file hardcodes a real credential instead of calling `env(...)`, that credential ships in your repository history. Keep every secret behind an `env()` call with no committed default, and inject the real value at deploy time.

## What you learned {.recap}

| Concept | What it does |
|---|---|
| `Config` | A typed, fail-fast accessor (`string()`/`int()`/`bool()`/`array()`) over Laravel's own config repository |
| `#[ConfigProperties(prefix)]` | Binds a config subtree onto a plain DTO, registered as a container singleton |
| `ReflectionConfigBinder` | The default `ConfigBinder`: matches constructor parameters by name, coerces scalars, recurses into nested DTOs |
| `ConfigPropertiesScanner` / `ConfigManifestCompiler` | Reflects `#[ConfigProperties]` classes once, at `firefly:cache` time, into a zero-reflection manifest |
| `ConfigRegistrar` | Binds every manifest entry as a singleton, and installs `ConfigValueResolver` over the container's default |
| `#[Value('${key:default}')]` | With `firefly/config` installed, resolves against application config first, then the environment, then the default |
| `ProfileResolver` / `Profiles` | Resolves active profiles from `FIREFLY_PROFILES_ACTIVE`, falling back to `APP_ENV`, falling back to `default` |
| `#[ConditionalOnProfile(...)]` | Gates a component's presence in the container on one or more active profiles |

## Try it yourself {.exercises}

1. **Add `WalletProperties` for real.** Create `config/wallet.php` and `Lumen\Domain\WalletProperties` exactly as shown in this chapter (in a scratch copy of the project — do not modify the shipped `samples/lumen` package), constructor-inject it into a new service, and confirm `php artisan firefly:cache` followed by reading the injected DTO reflects a value you set via `WALLET_DAILY_TRANSFER_LIMIT_MINOR` in `.env`.
2. **Force a missing-key failure.** Remove the constructor default from one of `WalletProperties`'s parameters, delete the corresponding key from `config/wallet.php`, and observe `ConfigurationException` at the point the DTO is resolved — then restore the default and confirm the exception disappears.
3. **Gate a bean to a profile.** Add a `#[Component]` `#[ConditionalOnProfile('testing')]` class to your scratch project, run `php artisan firefly:cache` with `FIREFLY_PROFILES_ACTIVE` unset, and confirm the class never appears in the compiled component manifest; then re-run the cache with `FIREFLY_PROFILES_ACTIVE=testing` and confirm it does.
