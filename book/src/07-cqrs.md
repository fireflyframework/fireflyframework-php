# CQRS: Commands and Queries {.chtitle}

By the end of this chapter you will know the shape of `firefly/cqrs`'s two buses (`CommandBus::send` / `QueryBus::ask`), how `#[CommandHandler]`/`#[QueryHandler]` register a handler as both a DI bean and a dispatch target — with the handled message type *inferred* from the handler's own `handle()` parameter — exactly what the bounded pipeline each bus runs looks like, how a handler's own exception surfaces to a caller wrapped in a `CommandProcessingException`/`QueryProcessingException`, how `#[CachedQuery]` puts a query's answer in a cache and `#[InvalidatesQuery]` takes it out again when the event that makes it stale commits, and how `HandlerScanner` compiles handler discovery into a manifest `firefly:cache` writes right alongside the component and route manifests you already met in Chapters 2 and 4.

!!! note "New term: CQRS"
    **Command Query Responsibility Segregation** treats writes and reads as two distinct kinds of message with two distinct dispatch paths — a **command** is an intent to change the write model and returns at most an id or a count; a **query** is a pure read that never mutates anything. `firefly/cqrs` gives each its own bus, its own handler attribute, and its own pipeline, so the two are never accidentally mixed at a single call site.

---

## Two buses, one shape

Both buses are one-method ports:

<!-- source: packages/cqrs/src/Command/CommandBus.php -->
```php
interface CommandBus
{
    public function send(object $command): mixed;
}
```

<!-- source: packages/cqrs/src/Query/QueryBus.php -->
```php
interface QueryBus
{
    public function ask(object $query): mixed;
}
```

`send` is the write-side verb; `ask` is the read-side verb — chosen deliberately over the more obvious `query()`, which would collide with Eloquent's own `Model::query()` at every call site inside a repository. Neither interface requires its message to implement anything: `Firefly\Cqrs\Command\Command` and `Firefly\Cqrs\Query\Query` exist purely as *optional* documentary markers —

<!-- source: packages/cqrs/src/Command/Command.php -->
```php
interface Command {}
```

— so a command is free to be exactly what `Lumen\Application\Command\OpenWallet` already is: a `final readonly` DTO with no base class and no interface at all:

<!-- source: samples/lumen/src/Application/Command/OpenWallet.php -->
```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Command;

use Lumen\Domain\Currency;

/**
 * Command: open a new wallet for an owner in a given currency. A plain readonly DTO — the CQRS bus needs no marker
 * interface (per docs/modules/cqrs.md); the handler is resolved by the command's class-string. The wallet id is
 * generated by OpenWalletHandler and returned to the caller.
 */
final readonly class OpenWallet
{
    public function __construct(
        public string $ownerId,
        public Currency $currency,
    ) {}
}
```

Dispatching one is a single call, whether it comes from a controller, a test, or another service:

<!-- illustrative: the one call a reader makes against the bus from their own code -->
```php
/** @var CommandBus $commands */
$walletId = $commands->send(new OpenWallet('owner-A', Currency::EUR));
```

`$commands->send()` returns *whatever the handler returns* — here, the freshly minted wallet id — because `send()`/`ask()` are typed `mixed`. The bus itself has no idea what an `OpenWallet` even means; that is entirely the handler's job, which is exactly what the next section builds.

## Handlers: one attribute, two jobs

`#[CommandHandler]` and `#[QueryHandler]` both **specialise** `#[Component]` from Chapter 2 — they *extend* it rather than merely resembling it:

<!-- source: packages/cqrs/src/Attributes/CommandHandler.php -->
```php
#[Attribute(Attribute::TARGET_CLASS)]
final class CommandHandler extends Component
{
    public function __construct(public readonly ?string $command = null)
    {
        parent::__construct();
    }
}
```

<!-- source: packages/cqrs/src/Attributes/QueryHandler.php -->
```php
#[Attribute(Attribute::TARGET_CLASS)]
final class QueryHandler extends Component
{
    public function __construct(public readonly ?string $query = null)
    {
        parent::__construct();
    }
}
```

Because of that `extends Component`, one attribute does **two** independent jobs at once: `ComponentScanner` (Chapter 2) discovers the class through `ReflectionAttribute::IS_INSTANCEOF` matching exactly as it would a `#[Service]`, so the handler becomes a constructor-injected singleton bean with **no separate `#[Service]` needed** — and `firefly/cqrs`'s own `HandlerScanner` reads the very same attribute to build the command/query dispatch table. Here is the whole, real handler behind `OpenWallet` — `samples/lumen/src/Application/Command/OpenWalletHandler.php`:

<!-- source: samples/lumen/src/Application/Command/OpenWalletHandler.php -->
```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Command;

use Firefly\Cqrs\Attributes\CommandHandler;
use Firefly\Data\Transaction\Attributes\Transactional;
use Lumen\Domain\Wallet;
use Lumen\Infrastructure\WalletRepository;

/**
 * Handles OpenWallet: mints a new wallet id, opens the aggregate, and persists it. The handled command type is
 * inferred from the sole handle() parameter (HandlerScanner param inference) — no explicit #[CommandHandler(...)].
 *
 * #[Transactional] is LOAD-BEARING, not cosmetic: DefaultCommandBus opens no transaction of its own, and
 * EloquentRepository::save() only tracks the aggregate when transactionLevel() > 0. The generated transactional proxy
 * installs the TransactionTemplate that is the sole caller of DomainEventDispatcher::dispatchAfterCommit(), so without
 * this attribute the WalletOpened domain event would never publish and S5's ledger projector would never fire.
 *
 * Intentionally NOT final: the generated transactional proxy subclasses this handler (mirroring the framework's own
 * SignatureBag/TxWidget fixtures and the PlaceOrderService pattern in docs/modules/domain.md).
 */
#[CommandHandler]
class OpenWalletHandler
{
    public function __construct(private readonly WalletRepository $wallets) {}

    #[Transactional]
    public function handle(OpenWallet $command): string
    {
        $id = 'wlt-'.bin2hex(random_bytes(8));
        $wallet = Wallet::open($id, $command->ownerId, $command->currency);
        $this->wallets->save($wallet);

        return $id;
    }
}
```

Notice `#[CommandHandler]` here carries **no argument** — `OpenWallet::class` is never written anywhere in this file. `HandlerScanner` — the one reflection site in the whole package — resolves the handled message type by reading `handle()`'s own parameter:

<!-- source: packages/cqrs/src/Scanner/HandlerScanner.php -->
```php
final class HandlerScanner
{
    // …
    private function messageType(ReflectionClass $reflection, ?string $explicit, string $handlerClass): string
    {
        if ($explicit !== null) {
            return $explicit;
        }

        if (! $reflection->hasMethod('handle')) {
            throw new CqrsConfigurationException("Handler [{$handlerClass}] declares no public handle() method. Add handle(<Message>) or an explicit #[CommandHandler(Message::class)].");
        }

        $parameters = $reflection->getMethod('handle')->getParameters();
        if (count($parameters) !== 1) {
            throw new CqrsConfigurationException("Handler [{$handlerClass}]::handle() must take exactly one message parameter, got ".count($parameters).'.');
        }

        $type = $parameters[0]->getType();
        if (! $type instanceof ReflectionNamedType || $type->isBuiltin()) {
            throw new CqrsConfigurationException("Cannot infer the message type for [{$handlerClass}]::handle() from its parameter. Annotate #[CommandHandler(Message::class)] / #[QueryHandler(Message::class)] explicitly.");
        }

        return $type->getName();
    }
// …
}
```

Same rule Chapter 6 already showed you for `#[EventListener]`'s sibling scanner. An explicit `#[CommandHandler(OpenWallet::class)]` always wins if present — useful when `handle()` takes a shared base type or an `object` parameter the scanner cannot narrow — but for the common case of one handler, one concrete message, one typed parameter, you never write the class name twice. Get the shape wrong — no `handle()` method, more than one parameter, a scalar/union parameter type the scanner can't resolve to a class — and `HandlerScanner` throws `CqrsConfigurationException` at **cache time**, not at some later request.

The query side is the mirror image, and reads a query with no side effects at all — `GetBalanceHandler`, real, shipped code:

<!-- source: samples/lumen/src/Application/Query/GetBalance.php -->
```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Query;

use Firefly\Cqrs\Attributes\CachedQuery;

/**
 * Query: read a wallet's current balance in minor units. GetBalanceHandler returns null for an unknown wallet.
 *
 * Cached for 60 seconds once firefly.cqrs.query.cache.provider=cache, keyed by its one public property: two
 * GetBalance('w-1') share an entry, GetBalance('w-2') has its own. A null answer is never cached. FundsDeposited and
 * FundsWithdrawn evict the entry of the wallet they changed, so the TTL only bounds staleness from writes that bypass
 * the bus.
 */
#[CachedQuery(ttl: 60)]
final readonly class GetBalance
{
    public function __construct(public string $walletId) {}
}
```

<!-- source: samples/lumen/src/Application/Query/GetBalanceHandler.php -->
```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Query;

use Firefly\Cqrs\Attributes\QueryHandler;
use Lumen\Infrastructure\WalletRepository;

/**
 * Handles GetBalance: reads the aggregate through the port and returns its balance in minor units, or null when no
 * such wallet exists. A pure read — no #[Transactional]; the query type is inferred from the handle() parameter.
 */
#[QueryHandler]
final class GetBalanceHandler
{
    public function __construct(private readonly WalletRepository $wallets) {}

    public function handle(GetBalance $query): ?int
    {
        $wallet = $this->wallets->findById($query->walletId);

        return $wallet?->balanceMoney()->minorUnits;
    }
}
```

`GetBalanceHandler` is `final` and carries no `#[Transactional]` at all — a query never mutates state, so there is no unit of work to demarcate and nothing for a proxy to intercept. `GetLedgerHandler` (behind Chapter 4's `WalletController::ledger()`) is the same shape reading `LedgerEntry` rows straight back:

<!-- source: samples/lumen/src/Application/Query/GetLedgerHandler.php -->
```php
<?php

declare(strict_types=1);

namespace Lumen\Application\Query;

use Firefly\Cqrs\Attributes\QueryHandler;
use Lumen\Domain\LedgerEntry;

/**
 * Handles GetLedger: returns the wallet's ledger rows in insertion order. S5's projector writes `ledger_entries`, so
 * this reads the projected rows directly (an empty list for a wallet with no entries yet). A pure read —
 * no #[Transactional]; the query type is inferred from the handle() parameter.
 */
#[QueryHandler]
final class GetLedgerHandler
{
    /** @return list<LedgerEntry> */
    public function handle(GetLedger $query): array
    {
        return array_values(
            LedgerEntry::query()
                ->where('wallet_id', $query->walletId)
                ->orderBy('id')
                ->get()
                ->all()
        );
    }
}
```

!!! laravel "Laravel parity"
    Plain Laravel has no read/write split at the dispatch layer at all — you either `dispatch()` a queued job or call a service method directly, and nothing stops a "query" object from quietly mutating something. `#[CommandHandler]`/`#[QueryHandler]` make the split a first-class, attribute-discovered concept: a query handler that tried to call `$this->wallets->save(...)` would still compile, but it would be an obvious code-review red flag, because nothing about `QueryBus::ask()`'s pipeline (no transaction, no domain-event drain) supports it.

## The bounded pipeline

Neither bus is a bare function call to the handler. `DefaultCommandBus::send()` — the shipped implementation — runs a small, fixed sequence of collaborators around the dispatch:

<!-- source: packages/cqrs/src/Command/DefaultCommandBus.php -->
```php
final class DefaultCommandBus implements CommandBus
{
    // …
    public function __construct(
        private readonly HandlerRegistry $registry,
        private readonly MessageValidator $validator,
        private readonly CommandAuthorizer $authorizer,
        private readonly CorrelationContext $correlation,
        private readonly CqrsMetrics $metrics,
    // …
    public function send(object $command): mixed
    {
        $prior = $this->correlation->begin();
        $startedAt = microtime(true);

        try {
                // …
                $this->validator->validate($command);
                $this->authorizer->authorize($command);

                $handler = $this->registry->findCommandHandler($command::class);
            // …
            $this->metrics->recordCommandSuccess($command, microtime(true) - $startedAt);

            return $result;
        } catch (Throwable $e) {
            $this->metrics->recordCommandFailure($command, microtime(true) - $startedAt);

            throw $e instanceof CommandProcessingException ? $e : new CommandProcessingException($command::class, $e);
        } finally {
            $this->correlation->end($prior);
        }
    }
}
```

Read it as **correlate → validate → authorize → resolve + invoke the handler → metrics**, wrapped in a `try`/`catch`/`finally` that guarantees the correlation id is restored no matter what happens. `DefaultQueryBus::ask()` is the same shape with one extra step — a cache short-circuit — inserted between authorize and invoke:

<!-- source: packages/cqrs/src/Query/DefaultQueryBus.php -->
```php
final class DefaultQueryBus implements QueryBus
{
    // …
    public function ask(object $query): mixed
    {
        $prior = $this->correlation->begin();
        $startedAt = microtime(true);

        try {
                // …
                $this->validator->validate($query);
                $this->authorizer->authorize($query);

                $policy = $this->policies?->policyFor($query::class);
                $key = match (true) {
                    $query instanceof Cacheable => $query->cacheKey(),
                    $policy !== null => QueryCacheKey::of($query),
                    default => null,
                };
                $group = $policy !== null ? $policy->group : '';
                $ttl = $policy->ttl ?? $this->cacheTtl;

                if ($key !== null) {
                    $cached = $this->cache instanceof GroupedQueryCache
                        ? $this->cache->lookup($group, $key)
                        : $this->cache->get($key);
                    if ($cached !== null) {
                        return $cached;
                    }
                }

                $handler = $this->registry->findQueryHandler($query::class);
                $result = $handler($query);

                if ($key !== null) {
                    if ($this->cache instanceof GroupedQueryCache) {
                        $this->cache->store($group, $key, $result, $ttl);
                    } else {
                        $this->cache->put($key, $result, $ttl);
                    }
                }
            // …
            $this->metrics->recordQuerySuccess($query, microtime(true) - $startedAt);

            return $result;
        } catch (Throwable $e) {
            $this->metrics->recordQueryFailure($query, microtime(true) - $startedAt);

            throw $e instanceof QueryProcessingException ? $e : new QueryProcessingException($query::class, $e);
        } finally {
            $this->correlation->end($prior);
        }
    }
}
```

Every collaborator except `HandlerRegistry` itself defaults to a **no-op**, so the pipeline is a chain of stages you can light up one at a time rather than an all-or-nothing framework:

| Stage | Default | What lights it up |
|---|---|---|
| Validation | Skipped unless the message implements `Validatable` | The shipped `firefly/validation` `Validator` |
| Authorization | `AllowAllAuthorizer` — allow everything | `firefly/security`'s `SecurityCommandAuthorizer`/`SecurityQueryAuthorizer` (Chapter 10) |
| Correlation | Always on — a uuid4 id per dispatch, restored after | Nothing to enable; stamped into `x-correlation-id` when a domain event reaches the eda bus (Chapter 8) |
| Metrics | `NoOpCqrsMetrics` | `firefly/observability` (a later chapter) |
| Query cache | `NoOpQueryCache` — always a miss | `firefly.cqrs.query.cache.provider=cache` (`CacheQueryCache` on a Laravel cache store) for `Cacheable` and `#[CachedQuery]` queries |

Neither bus opens a transaction, and neither bus drains domain events. `#[Transactional]` on `OpenWalletHandler::handle()` above is doing that work entirely on its own, through the generated proxy Chapter 9 explains in full — the bus is completely oblivious to it, and would behave identically if `handle()` were a plain, unproxied method that happened to call `DB::beginTransaction()` by hand.

## When a handler throws: category-preserving wrapping

`WithdrawHandler`'s `handle()` can fail two very different ways — the wallet might not exist, or the domain's own no-overdraw invariant might refuse the amount. Either way, `send()`'s `catch` block wraps whatever was thrown:

<!-- source: packages/cqrs/src/Exception/CommandProcessingException.php -->
```php
final class CommandProcessingException extends CqrsException
{
    public function __construct(string $commandClass, Throwable $cause)
    {
        parent::__construct(
            "Processing command [{$commandClass}] failed: {$cause->getMessage()}",
            // …
            $cause instanceof FireflyException ? $cause->httpStatus() : 500,
            $cause instanceof FireflyException ? $cause->category() : ErrorCategory::Internal,
            $cause instanceof FireflyException ? $cause->severity() : ErrorSeverity::Error,
            $cause,
        );
    }
}
```

Three things to notice. First, the cause is always available on `getPrevious()` — the constructor's fifth argument to the parent — so nothing about the original failure is lost, only wrapped. Second, this is **category-preserving**: when the cause is a `FireflyException` (every kernel exception is), its own `httpStatus()`/`category()`/`severity()` are copied onto the wrapper rather than defaulting to a generic `500`/`Internal`. A `ResourceNotFoundException` (404, business) thrown for an unknown wallet id still renders as a 404 problem-details response even after being wrapped — the bus adds context, it never masks the fault. Third, `send()` checks `$e instanceof CommandProcessingException` before wrapping, so a nested command dispatch (a handler that itself calls `$commands->send(...)`) never gets double-wrapped in two layers of the same exception. `QueryProcessingException` is the read-side twin, identical in shape.

`HandlerRegistry` throws its own, narrower exceptions for a **wiring** mistake rather than a business fault — an unmapped message sent through the bus:

<!-- source: packages/cqrs/src/Handler/HandlerRegistry.php -->
```php
final class HandlerRegistry
{
    // …
    public function findCommandHandler(string $commandClass): callable
    {
        return $this->commandHandlers[$commandClass] ?? throw new CommandHandlerNotFoundException($commandClass);
    }
// …
}
```

`CommandHandlerNotFoundException`/`QueryHandlerNotFoundException` are both `ErrorCategory::Framework`, `500` — a genuinely different signal from a `ConflictException`'s `409`: the first means "nothing was ever registered for this message," the second means "something *was* registered, and it correctly refused the request." The registry also refuses a **second** registration for the same message class outright:

<!-- source: packages/cqrs/src/Handler/HandlerRegistry.php -->
```php
final class HandlerRegistry
{
    // …
    public function registerCommandHandler(string $commandClass, callable $invoker): void
    {
        if (isset($this->commandHandlers[$commandClass])) {
            throw new CqrsConfigurationException("Duplicate command handler registered for message [{$commandClass}]. One command maps to exactly one handler.");
        }

        $this->commandHandlers[$commandClass] = $invoker;
    }
// …
}
```

One command, one handler — enforced at wiring time, not left to whichever registration happened to run last.

!!! tip "Unwrapping the cause in a test"
    A test that wants to assert *why* a command was rejected reaches straight past the wrapper with `getPrevious()`. `samples/lumen/tests/Application/TransferSecurityTest.php` does exactly this for a denied `#[PreAuthorize]` (Chapter 10 explains the guard itself):

<!-- illustrative: the unwrap a reader writes in their own test -->
```php
$denied = null;
try {
    $commands->send(new Withdraw($walletId, 1000));
} catch (CommandProcessingException $e) {
    $denied = $e;
}

expect($denied)->toBeInstanceOf(CommandProcessingException::class);
expect($denied?->getPrevious())->toBeInstanceOf(AuthorizationException::class);
```

The outer type tells you *which bus operation* failed; the inner type — reached via `getPrevious()` — tells you *why*.

## Caching queries: `#[CachedQuery]` and `#[InvalidatesQuery]`

The pipeline table above names a query-cache stage that misses by default. Setting `firefly.cqrs.query.cache.provider=cache` swaps `NoOpQueryCache` for `CacheQueryCache`, which keeps a query's answer on a Laravel cache store, and two attributes decide what is cached and what makes it stale. Lumen's balance read is the natural candidate — every wallet screen asks for it, and it changes only when money moves:

<!-- source: samples/lumen/src/Application/Query/GetBalance.php -->
```php
#[CachedQuery(ttl: 60)]
final readonly class GetBalance
{
    public function __construct(public string $walletId) {}
}
```

The key is the query value itself. `CacheQueryCache` derives it from the query's class and its public properties, so two `GetBalance('w-1')` objects share one entry and `GetBalance('w-2')` gets its own. A `null` answer — an unknown wallet — is never stored; a query holding private or protected state cannot be keyed and simply runs uncached; and a cache that fails is logged and bypassed, because a cache may make a query faster but must never make it fail. `ttl: 60` bounds how long an entry lives, falling back to `firefly.cqrs.query.cache_ttl`; `group:` (by default the query class) names the set one eviction can clear at once.

The other half belongs to the event. A cached balance is wrong the moment a deposit commits, and the event is the one thing that knows it, so the rule is written on the event class:

<!-- source: samples/lumen/src/Domain/Event/FundsDeposited.php -->
```php
#[PublishDomainEvent('wallet.events')]
#[InvalidatesQuery(GetBalance::class, with: ['walletId' => 'walletId'])]
final readonly class FundsDeposited extends DomainEvent
{
    public function __construct(
        public string $walletId,
        public int $amountMinor,
        public string $currency,
        public int $balanceMinor,
    ) {
        parent::__construct();
    }
}
```

`with:` maps each public property of the query to a property of the event, so the eviction removes exactly one entry: the wallet that changed. `HandlerScanner` refuses a map that names an unknown property or leaves one out — at `firefly:cache` time, not in production, because a wrong map would derive a key no entry has and miss silently. The eviction runs when the event is dispatched after its transaction commits, so a rolled-back deposit evicts nothing, and it runs again, matched by event type, when the same event arrives over the event bus from another process. Leave `with:` out and the whole group goes; write `key: 'statement:{account}'` and a `Cacheable` query's own key template is evicted instead. `FundsWithdrawn` carries the same attribute.

The sample proves the behavior that matters, with the cache switched on in `LumenQueryCacheTestCase` (`cache.default=array`, `provider=cache`) and nowhere else:

<!-- source: samples/lumen/tests/Application/QueryCacheTest.php -->
```php
    expect($queries->ask(new GetBalance($id)))->toBe(1000);

    // Changed behind the bus's back: the cached answer does not see it.
    DB::table('wallets')->where('id', $id)->update(['balance_minor' => 5000]);
    expect($queries->ask(new GetBalance($id)))->toBe(1000);

    // A committed deposit raises FundsDeposited, whose #[InvalidatesQuery] evicts exactly this wallet's balance.
    $commands->send(new Deposit($id, 500));
    expect($queries->ask(new GetBalance($id)))->toBe(5500);
```

The second answer is the cached one — the row changed under it and it did not notice, which is the whole point of a cache and the whole risk of one. The deposit evicts the entry, and the next read is the database's again: 5000 plus 500. The same file proves that a deposit into wallet A leaves wallet B's cached balance alone, and that a withdrawal evicts like a deposit does.

Groups are evicted by **generations**, not cache tags, so eviction works on every store, `file` and `database` included: an evicted entry becomes unreachable at once and expires on its TTL, which is why setting one is worth it. The reference configuration ships the block commented out:

<!-- source: skeleton/config/firefly.php -->
```php
// 'query' => [
//     'cache_ttl' => 60,
//     'cache' => [
//         'provider' => env('FIREFLY_CQRS_QUERY_CACHE', 'none'),
//         'store' => env('FIREFLY_CQRS_QUERY_CACHE_STORE', ''),
//         'prefix' => 'firefly:cqrs:',
//         'invalidation' => [
//             'ledger.closed' => [App\Ledger\LedgerTotals::class],
//         ],
//     ],
// ],
```

!!! warning "The key is the value object"
    A query whose answer depends on the tenant or the signed-in user must carry them as public properties. `GetBalance` is safe because the wallet id is the whole question; a `MyWallets` query with no `ownerId` property would hand every user the first user's list.

!!! note "Why a domain event names a query"
    `FundsDeposited` now imports `GetBalance`, an application-layer class, the same way it already carries `#[PublishDomainEvent]`. The framework puts the rule there on purpose — the event is what knows what it makes stale — and it buys the precise, one-wallet eviction. The alternative, `firefly.cqrs.query.cache.invalidation` (event type ⇒ query classes, for events this process has no class for), keeps the domain clean and evicts every wallet's balance on every deposit.

## Compiled, not reflected: `HandlerScanner` → `HandlerManifest` → `firefly:cache`

`HandlerScanner` is the **sole** reflection site in `packages/cqrs/src` (the same grep-enforced invariant Chapter 6 described for `firefly/domain`). It walks the app's PSR-4 roots once, resolves every `#[CommandHandler]`/`#[QueryHandler]` (running exactly the `messageType()` inference you just read) into a `HandlerDescriptor`, and hands the whole list to `HandlerManifestCompiler`, which `var_export()`s it to a plain PHP array file — the same zero-reflection technique Chapter 2 introduced for the component manifest and Chapter 3 for `#[ConfigProperties]`.

You never run `HandlerScanner` yourself. It is one of the **fourteen** scanner/compiler pairs `php artisan firefly:cache` orchestrates in one pass, alongside the component/context, route, config-properties, and (Chapter 9's) transactional scanners:

```bash
$ php artisan firefly:cache
firefly:cache — wrote 16 manifest(s) + 1 proxy(ies) to /path/to/my-app/bootstrap/cache/firefly
```

The compiled file lands at `bootstrap/cache/firefly/handlers.php`; `FireflyCacheServiceProvider` binds it straight onto the `HandlerManifest` container entry — unconditionally overriding the **empty** default `CqrsWiringProvider` binds when no cache exists yet (the same `#[ConditionalOnMissingBean]`-style backing-off pattern Chapter 2 showed you for beans, applied here to a whole compiled manifest). `CqrsHandlerWiringPass` then walks that manifest at boot and populates the `HandlerRegistry` you met above with one invoker per descriptor — each invoker resolving its handler bean **fresh from the container on every dispatch**, never cached at wiring time, so a `#[Transactional]` handler like `OpenWalletHandler` is always observed through its generated proxy (Chapter 9), never through the bare, unproxied class.

Get this wrong in an application — add a handler, forget to re-run `firefly:cache` — and the message it should have handled resolves nothing: `HandlerRegistry::findCommandHandler()` never sees the new descriptor, and dispatching that command throws `CommandHandlerNotFoundException` until the cache is regenerated. Fail loud at cache time (a malformed handler) or fail loud at dispatch time (a stale cache) — never a silent no-op.

## What you learned {.recap}

| Concept | What it does |
|---|---|
| `CommandBus::send(object): mixed` / `QueryBus::ask(object): mixed` | The two dispatch ports; a command may mutate and returns at most an id, a query never mutates |
| `#[CommandHandler]` / `#[QueryHandler]` | Specialise `#[Component]` — one attribute registers the handler as a DI bean **and** a dispatch target |
| Message-type inference | `HandlerScanner` reads the sole `handle()` parameter unless an explicit class-string is given |
| The bounded pipeline | correlate → validate → authorize → (cache-get, query only) → resolve + invoke → (cache-put, query only) → metrics |
| `#[CachedQuery]` / `#[InvalidatesQuery]` | Caches a query's answer by value on a Laravel store (`firefly.cqrs.query.cache.provider=cache`); the event that makes it stale evicts one entry (`with:`) or a group after it commits |
| `CommandProcessingException` / `QueryProcessingException` | Category-preserving wrappers; the original fault is always reachable via `getPrevious()` |
| `HandlerRegistry` | One command/query class maps to exactly one handler — a duplicate registration fails loud at wiring time |
| `HandlerScanner` → `HandlerManifest` | The sole reflection site; compiled by `firefly:cache` (one of fourteen scanner/compiler pairs) into a zero-reflection manifest |

## Try it yourself {.exercises}

1. **Trigger `CommandHandlerNotFoundException`.** In a scratch copy of the project (not the shipped `samples/lumen` package), define a new command class with no `#[CommandHandler]` anywhere in the app, dispatch it through `CommandBus::send()`, and confirm you get a `CommandHandlerNotFoundException` wrapped in nothing (it is thrown directly by the registry, before the bus's own `catch` block would wrap a handler's fault).
2. **Force an ambiguous `handle()`.** Give a `#[QueryHandler]` class a `handle()` method with two parameters (or a parameter typed `object`) and run `php artisan firefly:cache`. Confirm it fails loud with `CqrsConfigurationException` naming the exact class and method, rather than silently skipping the handler.
3. **Read the compiled manifest.** After running `firefly:cache` in a project with `OpenWalletHandler` and `GetBalanceHandler` present, open `bootstrap/cache/firefly/handlers.php` and find both entries. Match each array's `kind` field (`'command'` or `'query'`) back to the `HandlerKind` enum this chapter described.
4. **Break an eviction on purpose.** In a scratch copy of the project, delete the `#[InvalidatesQuery]` line from `FundsWithdrawn` and run `samples/lumen/tests/Application/QueryCacheTest.php`. Confirm that only the withdrawal test fails, with the old balance, then restore the line.
